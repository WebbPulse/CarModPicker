## Issues Found

### Advisory (non-blocking)

**A-01 — `bg_log_context` defined but unused in `backend/app/`**

- **File:** `backend/app/core/log_context.py:17-34` (definition), `backend/tests/test_log_propagation.py:123-155` (unit tests)
- **Severity:** Advisory / informational — NOT a regression
- **Affected REQ-IDs:** OBS-04
- **Finding:** The `bg_log_context(task_name, job_id)` context manager is defined and unit-tested, and its docstring says "Use this to wrap crawler runner, orphan-job sweep, EventBridge callback handlers — any code that logs outside a request scope." However, `grep -rn "bg_log_context" backend/app/` returns only two hits, both in **comments** (`runner.py:56`, `ecs_runner.py:143`, `sentry.py:49,94`). No production code actually invokes the context manager. Instead, all three entry points set the underlying ContextVars directly:
  - `ecs_runner.py:108-109`: `request_id_var.set(f"ecs:{os.getpid()}:{job_id or '-'}")` + `user_id_var.set("ecs")`
  - `ecs_rescrape_runner.py` (imports both vars at L83, sets them directly at entry)
  - `__main__.py:19-20`: `request_id_var.set(f"cli:{os.getpid()}")` + `user_id_var.set("cli")`
  - Lifespan orphan-job sweep in `main.py:87-132` — does NOT wrap the sweep in `bg_log_context` despite the docstring explicitly citing "orphan-job sweep" as an intended use case.
- **Why this is NOT a regression:** `ecs_runner.py:138-147` explicitly documents the choice: "ECS tasks never re-enter, so the explicit set() without a reset token is sufficient — we don't need `bg_log_context`'s re-entrant-safe reset semantics." Log propagation to CloudWatch and Sentry works correctly on all paths because `RequestContextFilter` (logging.py:82,98) and the Sentry `_before_send` scope processor (sentry.py:91-101) both read the raw ContextVars, not through `bg_log_context`. Tests in `test_log_propagation.py` verify the helper works in isolation; they don't assert that production code uses it.
- **Why it's worth noting:** The lifespan orphan-job sweep at `main.py:102-132` runs inside a request that has request_id="-" / user_id="-" (the ContextVar defaults), because the sweep runs on FastAPI startup before any request middleware sets the vars. Any exception or log line from `crawler_schedule_service.sweep_orphan_schedules` or `job_service.sweep_orphan_jobs` will be tagged `request_id=-` in CloudWatch — not `request_id=bg:orphan-sweep:-` as the `bg_log_context` docstring implies would be useful. This is a grepability/observability gap, not a correctness gap.
- **Recommended action:** EITHER (a) update the `bg_log_context` docstring to remove "orphan-job sweep" from the listed use cases (since the pattern intentionally isn't used there), OR (b) in a future phase, wrap the two sweep blocks in `main.py:lifespan` with `with bg_log_context("orphan-sweep"):` to match the docstring's advertised behavior. Not a v1.0 blocker.
