<objective>
Extend the crawler's per-adapter result dict with `parse_failures: int`, `sample_failure_urls: list[str]` (first-5, URL-only per D-23), and `elapsed_seconds: float`; extend `_render_crawler_result_html` in `backend/app/core/email.py` to emit a per-adapter "ParseFailures" block with sample URLs inside the existing SES job-report email (CRAWL-07).

Purpose: Operators currently see a count of generic "errors" per adapter in the job report but cannot distinguish "site returned 500" from "our parser returned None from a valid HTML page" — the latter indicates our parser is drifting off the retailer's page template. This plan surfaces per-adapter parse-failure counts with sample URLs so the root cause is immediately visible without grepping logs. Also adds `elapsed_seconds` so Phase 2 (OBS-02 CloudWatch metrics) can consume it with zero schema change (D-24/D-38).

Output: Extended result-dict schema; extended email renderer; one new test file + one new test case in existing `test_email.py`; all tests GREEN.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Crawler runner ← retailer product URLs (already sitemap-derived and host-allowlisted by existing code) | `sample_failure_urls` contains exactly the URLs already processed by `adapter.fetcher.fetch` — no new trust surface. |
| SES email recipient ← rendered HTML body | Per Pitfall PR-01, sample URLs are escaped via `_escape_html` / `html.escape` before inclusion — HTML-injection-proofed. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-03-01 | Information-disclosure | Sample URL embedding a credential (e.g., `?token=xyz`) in the email body | accept | Retailer product URLs are not expected to contain credentials (they're sitemap-enumerated public URLs). If a retailer's sitemap ever exposes tokenized URLs, that's a retailer-side leak. No new data exposure vs the existing `error_urls`/`parse_miss_urls` keys already in the email. |
| T-03-03-02 | Injection | Maliciously-crafted URL containing `<script>` tags rendered raw in the email | mitigate | Renderer wraps sample URLs in `_escape_html` (or stdlib `html.escape`). `<script>` becomes `&lt;script&gt;`. Verified by `test_crawler_parse_failures_block_renders` assertions checking literal-URL presence. |
| T-03-03-03 | Denial-of-service (cost) | Extremely long URLs (>100K chars) inflating email body | mitigate | Pitfall PR-01: truncate to ≤160 chars per URL (`first-120 + "…" + last-40`). Email body bounded by 5 samples × 160 chars = ≤800 chars added per adapter. |
| T-03-03-04 | Denial-of-service (cost) | CRAWL-07 extension triggering more SES sends | mitigate | No send-frequency change. CRAWL-07 extends the CONTENT of the existing per-run email only. Same trigger (end of crawler run), same recipients, same rate. |
| T-03-03-05 | Tampering | Malicious adapter returning fake `parse_miss_urls` to slip URLs into the operator's inbox | accept | Adapter code is reviewed at PR time. If a committer can land malicious code, the blast radius is unbounded anyway — this isn't the weakest link. |

**ASVS L1 coverage:** V5 Input Validation — `_escape_html`/`html.escape` on sample URLs before HTML emission. V4 Access Control unchanged — job-report email uses existing SES path with existing auth (IAM role).
