## Phase Boundary

Lock in the safety floor for the entire milestone: CI enforces backend + frontend coverage floors, a migration DROP-guard catches destructive schema changes, characterization tests pin current auth and crawler-adapter behavior before any refactor touches them, and three broken `op.drop_constraint(None, ...)` migrations are repaired with an explicit SQLAlchemy `MetaData.naming_convention` so every future autogenerate produces named constraints.

This phase is purely protective — it adds gates and characterization tests. It does NOT restructure any code, split any router, or change any external contract. Phases 2–6 depend on this scaffolding to ship safely.

<decisions>
## Implementation Decisions

### Backend coverage floor (SAFE-01)
- **D-01:** Measure the baseline first: run `pytest -n auto --cov=app --cov-report=term` on `main` and record the total line-coverage percentage in the PR description.
- **D-02:** Set `--cov-fail-under=<measured_baseline>` in `backend/pytest.ini` at the exact measured number (no buffer). Rationale: prevents silent drift; if a PR accidentally reduces coverage by any measurable amount it fails CI. If baseline is flaky across runs, round DOWN to the nearest whole percent.
- **D-03:** The baseline measurement and the `--cov-fail-under` update land in the same PR so the ratchet is atomic.

### Frontend CI tests + coverage (SAFE-02, SAFE-03)
- **D-04:** Add a `Run tests` step to `.github/workflows/frontend-ci.yml` running `npm test -- --run --coverage` before the existing `Build application` step (fail fast on test regressions before burning CI time on builds).
- **D-05:** `lines: 60` threshold is locked by SAFE-03. If the current frontend coverage is below 60, write enough tests to reach 60 in the same phase BEFORE enabling the threshold — do not land a red CI.
- **D-06:** Configure thresholds in `frontend/vitest.config.ts` under `coverage.thresholds` (`lines: 60`, `functions: 50`, `branches: 50`, `statements: 60` — conservative floors for the other dimensions so one easy metric doesn't mask regressions in the others).

### Migration DROP guard (SAFE-04)
- **D-07:** Implementation: a dedicated CI step in `backend-ci.yml` (not a pre-commit hook — keeps enforcement at the merge gate, not the developer machine).
- **D-08:** The step runs a small Python script (`backend/scripts/check_migrations.py`) that iterates every file in `backend/alembic/versions/*.py`, greps for `drop_column`, `drop_table`, `drop_constraint`, and requires a `# SAFE: <reason>` comment on the SAME line or the immediately preceding line. Missing annotation → non-zero exit.
- **D-09:** Annotation format is exactly `# SAFE: <human-readable reason>` — specific token so reviewers can grep for `SAFE:` to audit every destructive op across the history at any time.
- **D-10:** `alembic/versions/*.py` is the only scan path — we do not scan other Python for these tokens.

### Repair broken migrations + naming_convention (SAFE-08, SAFE-09)
- **D-11:** Apply SQLAlchemy `MetaData(naming_convention=...)` at `backend/app/db/base_class.py` using the SQLAlchemy-recommended convention (`ix_%(column_0_label)s`, `uq_%(table_name)s_%(column_0_name)s`, `ck_%(table_name)s_%(constraint_name)s`, `fk_%(table_name)s_%(column_0_name)s_%(referred_table_name)s`, `pk_%(table_name)s`). All FUTURE autogenerated constraints get deterministic names.
- **D-12:** Do NOT retroactively rename existing constraints. Generating a single sweep migration that renames every historic constraint to match the new convention is unsafe on the live RDS Postgres DB and out of scope for a safety-net phase.
- **D-13:** Repair the three broken migrations (`097024200e60`, `172d1c205fb3`, `6eae6b1393c5`) by replacing each `op.drop_constraint(None, <table>, type_='foreignkey')` with the actual constraint name inspected from the live DB (use `\d+ <table>` in psql against a Postgres-backed copy). Each repair migration carries a `# SAFE: repair invalid drop_constraint(None) — see SAFE-08` annotation.
- **D-14:** If a broken migration has already run on prod (most likely — these files are older), the repair is a down-migration + up-migration pair in a NEW migration file that asserts the intended FK state; do not rewrite history of already-applied migrations.

### Auth characterization tests (SAFE-06)
- **D-15:** Tool: `pytest-recording` (vcrpy-backed) — locked by REQUIREMENTS.md SAFE-06. Install as a backend dev dep, add to `requirements.txt` (or a future `requirements-dev.txt` if one emerges).
- **D-16:** The 7 happy-path flows covered, one test per flow:
  1. Signup → verify-email
  2. Login (email/password)
  3. 2FA-TOTP enrollment + challenge
  4. WebAuthn passkey registration + assertion
  5. Google OAuth sign-in
  6. Google OAuth account link (existing user)
  7. Password-reset request → reset
- **D-17:** Cassette strategy: cassettes stored under `backend/tests/cassettes/auth/`, committed to git, regenerated by deleting the cassette and re-running the test.
- **D-18:** External mocks: SES is already mocked via `moto` elsewhere — reuse that fixture. Google OAuth HTTP calls are VCR-recorded. WebAuthn cryptographic ceremony is stubbed at the `webauthn` library boundary (not over HTTP).
- **D-19:** Assertion depth: assert HTTP status code, presence of expected keys in response JSON, and database-state change where relevant (e.g., `email_verified=True`). Do NOT assert every field value — brittle and adds maintenance load. The point is "this flow still completes end-to-end," not exhaustive snapshot testing.

### Crawler adapter characterization tests (SAFE-07)
- **D-20:** Pick 5 adapters spanning fetcher tiers for representativeness:
  - 2× `tier0_http` (plain HTTP): pick two that were just fixed in commit 7831fda — e.g. `briantooleyracing`, `amsperformance` — so we pin the post-fix behavior.
  - 2× `tier1_flaresolverr` (JS-heavy, via FlareSolverr): pick the two most production-critical.
  - 1× `tier2_tls` (curl_cffi for anti-bot retailers): pick the most stable one.
- **D-21:** Fixture source: archived HTML from the crawl-data S3 bucket. Correct bucket names (amended 2026-04-22 — `carmodpicker-prod-user-images` was incorrect; that bucket holds user-uploaded images, not crawl archives): local/dev = `carmodpicker-local-crawl` (MinIO, `crawl_html/by_url/<hash>.html`); prod = `carmodpicker-production-crawl-data` (AWS S3, same key structure). Prefer local bucket first; fall back to prod if adapter data absent locally. Download one representative product page per adapter, commit the HTML under `backend/tests/crawlers/fixtures/<adapter_name>/product.html`.
- **D-22:** Test shape: feed the fixture HTML through `parse_product_page()` directly (bypass network), assert the parsed canonical-part fields (name, price, sku, image URLs) match a committed expected-output JSON. Do NOT test `discover_product_urls()` in this phase — URL filters are retailer-DOM brittle and not on any critical refactor path; revisit in Phase 3.
- **D-23:** Stable-API assertion: `RetailerCrawlerAdapter.ADAPTER_NAME` (see CRAWL-02) may not exist yet at phase 1 time. Tests key adapters by class name — switch to ADAPTER_NAME once Phase 3 lands.

### OpenAPI schema snapshot test (SAFE-05)
- **D-24:** Snapshot lives at `backend/tests/fixtures/openapi_snapshot.json`, committed to git.
- **D-25:** Test (`backend/tests/test_openapi_snapshot.py`) calls the FastAPI app's `.openapi()` method, serializes to JSON with stable key ordering, and asserts equality against the snapshot.
- **D-26:** On intentional schema change, the test fails; the fix is to regenerate the snapshot (`python -c "import json; from app.main import app; print(json.dumps(app.openapi(), indent=2, sort_keys=True))" > backend/tests/fixtures/openapi_snapshot.json`) and commit it alongside the schema change. The diff on that snapshot file IS the review artifact for schema drift.
- **D-27:** Do NOT use hash comparison — developers need to SEE the drift in PR review.

### Dependabot / dependency upgrades (SAFE-10)
- **D-28:** Use GitHub-native **Dependabot** (not Renovate). Rationale: zero extra infra, lower cognitive overhead, milestone is not dep-upgrade-heavy enough to justify Renovate's extra config surface.
- **D-29:** Weekly schedule (Mondays), three ecosystems: `pip` (backend/), `npm` (frontend/ + chrome-extension/), `github-actions` (workflows).
- **D-30:** Group minor + patch updates into one PR per ecosystem per week to reduce PR noise; major updates get individual PRs.
- **D-31:** Config lives at `.github/dependabot.yml`.

### Execution sequencing (within this phase)
- **D-32:** Internal order inside the phase: SAFE-09 (naming_convention) → SAFE-08 (repair 3 broken migrations) → SAFE-04 (DROP guard) → SAFE-01/02/03 (coverage gates) → SAFE-05 (OpenAPI snapshot) → SAFE-06 + SAFE-07 (characterization tests) → SAFE-10 (Dependabot). Rationale: establish naming convention BEFORE repairing migrations so the repairs use named constraints; land DROP guard BEFORE adding coverage gates so a regression PR can't slip `drop_` statements in while we're measuring baseline.

- Minor Dependabot groupings (dev dependencies group vs. prod group, etc.)

### Established Patterns
- **Alembic autogenerate-only** — SAFE-08 repair migrations must use `alembic revision --autogenerate` against a Postgres DB that has the broken state, then manually adjust the generated op to use the actual constraint name found via introspection. Hand-written migrations are forbidden per CLAUDE.md.
- **`ENABLE_RATE_LIMITING=false` in tests** — Existing characterization tests inherit this. Do NOT flip it on for auth characterization tests.

<specifics>
## Specific Ideas

- **"Fail at the PR gate, not the developer machine"** — Migration DROP guard is a CI step, not a pre-commit hook. Developers can keep fast local iteration; the enforcement is at merge.
- **"Measure first, gate second"** — Coverage floors are set AT the measured baseline. Not aspirational. Aspirations are set in follow-up PRs after more tests are written.
- **"The snapshot is the review artifact"** — OpenAPI snapshot is stored as formatted JSON, not a hash. The diff on that file in a PR IS how reviewers see schema drift — a hash would force them to regenerate locally.
- **"Characterization ≠ exhaustive"** — Assert flow completion + key presence, not every field value. The goal is to catch "this 7-step flow broke," not "this response field changed format."
- **Naming_convention is forward-only** — Do not retroactively rename existing constraints. Unsafe on live RDS, out of scope for a safety-net phase.

</specifics>
