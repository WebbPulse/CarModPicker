<objective>
Wave 5: Make part-linking operations pessimistic-lock-safe and prove the safety with a Postgres-backed 10-thread concurrency test.

Purpose: part_linker_service.py's three mutators (link_new_part, reelect_canonical, unlink_part) today read a canonical candidate then mutate it in a non-atomic window; two concurrent requests can produce orphaned or circular canonical references. with_for_update() serializes racing transactions on the canonical row. SQLite silently drops the directive (Pitfall 1), so the test MUST run on Postgres.

D-05 invariant refresher: "no orphans — every sibling's canonical_part_id resolves to a live Part row with canonical_part_id IS NULL." This implies unlink_part's lock scope cannot be limited to the subject row alone — a concurrent reelect_canonical reading the subject's canonical_part_id as non-null while an unlink is in flight can mutate a stale sibling set. The lock set for unlink_part must include the subject + its canonical (if any) + the full sibling set.

Output: A surgical addition of `select(DBPart).where(DBPart.id.in_(lock_ids)).with_for_update()` into three service functions (with D-05-compliant scope for unlink_part), a @pytest.mark.postgres test infrastructure (pytest.ini marker, conftest.py fixture, CI side-car with psql retry, docker-compose.test.yml), and a 10-thread concurrency test that proves the invariants.
</objective>

This body reads `part.canonical_part_id` and mutates only `part.canonical_part_id`. A NAIVE lock taken ONLY on `part.id` would leave the canonical row and the siblings exposed: a concurrent `reelect_canonical` (which reads `part.canonical_part_id`, then mutates that old canonical + every sibling via `_point_siblings_at`) could commit mutations against a canonical that this unlink is simultaneously detaching from.

**Insertion C — unlink_part (~:171-179) — D-05 compliant scope (BLOCKER 4):**

Replace the unlink_part body with:

```python
def unlink_part(db: Session, part: DBPart) -> DBPart:
    """Make ``part`` its own canonical, detaching it from its current link group.

    DATA-03 (Phase 4 D-01/D-05) lock scope: subject + canonical (if any) + siblings.
    The full sibling set must be locked so that a concurrent reelect_canonical
    cannot read subject.canonical_part_id as non-null and then mutate a stale
    sibling view. The invariant to preserve: every sibling's canonical_part_id
    resolves to a live Part row with canonical_part_id IS NULL.
    """
    # Lock the subject row first (stable ordering — subject.id is always in set).
    subject = db.scalars(
        select(DBPart).where(DBPart.id == part.id).with_for_update()
    ).one()

    canonical_id = subject.canonical_part_id
    if canonical_id is None:
        return subject

    # Lock the canonical row.
    db.scalars(
        select(DBPart).where(DBPart.id == canonical_id).with_for_update()
    ).one()

    # Lock every sibling that shares this canonical so any interleaving with
    # reelect_canonical / _point_siblings_at / another unlink serializes here.
    db.scalars(
        select(DBPart.id)
        .where(DBPart.canonical_part_id == canonical_id)
        .with_for_update()
    ).all()

    # Now safe to mutate.
    subject.canonical_part_id = None
    db.add(subject)
    db.flush()
    logger.info("Unlinked part %s from prior canonical", subject.id)
    return subject
```

**Preservation rules:**
- Do not change the algorithms (candidate scoring, sibling repointing, canonical selection).
- Do not add commit() / rollback() calls — the existing transaction scope (get_db generator) owns commit/rollback.
- Do not remove any existing algorithmic code. Lock reads are additive; the unlink_part body IS rewritten as shown above but the net behavior change is only lock acquisition ordering — the mutation remains `canonical_part_id = None` + `db.flush()`.

**Why these three sites:** D-05 explicit — the races occur at the candidate-read / canonical-mutation boundary. Locking candidates + canonical + siblings freezes the race window across all three operations.

**Deadlock-ordering note:** All three mutators acquire locks in ascending id order (via `.in_(lock_ids)` which Postgres serializes by the primary-key index). The subject row is locked first when the subject is known in advance (unlink_part, reelect_canonical); link_new_part locks via the `in_` clause directly.     """D-05 invariants under 10-thread contention on link_new_part."""
    shared_gtin = f"G{_worker_suffix()}{uuid.uuid4().hex[:12]}"
    _, _, part_ids = _seed(postgres_engine, shared_gtin)

    SessionLocal = sessionmaker(bind=postgres_engine, autocommit=False, autoflush=False)

    def link_one(part_id: uuid.UUID) -> uuid.UUID:
        with SessionLocal() as s:
            part = s.get(DBPart, part_id)
            assert part is not None, f"Seeded part {part_id} missing"
            link_new_part(s, part)
            s.commit()
            return part.id

        futures = [ex.submit(link_one, pid) for pid in part_ids]
        for f in as_completed(futures):
            f.result()  # re-raise any thread-level exception

            .select_from(DBPart)

        )
