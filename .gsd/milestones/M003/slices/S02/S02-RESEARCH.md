# S02 Research: Glass-card & legacy `:root` var purge — pass 1 reskin

## Summary

S02 is a small, surgical, structural slice. The legacy CSS layer survives until S04, so this slice does not delete anything from `index.css` — it just migrates the consumer files off the legacy class names and `var(--*)` calls onto either the existing `<Card variant="glass">` primitive (already shipped in M002/S08) or the equivalent inline Tailwind expression `bg-white/5 backdrop-blur-xl border border-white/10`.

The actual consumer surface is **9 files**, not "~8 high-traffic pages":

| `frontend/src/components/layout/globalFooter/Footer.tsx` | 3× `glass` (social-icon backgrounds) |
| `frontend/src/pages/Home.tsx` | 1× `<Card className="glass-card">` (line 385) |

| `frontend/src/pages/authentication/ExtensionAuth.tsx` | 1× `<div className="glass-card …">` |
| `frontend/src/pages/NotFound.tsx` | 1× `<div className="glass-card …">` |

| `frontend/src/pages/TermsOfService.tsx` | 1× `<div className="glass-card …">` |

`AccountAlerts.tsx` and `AdminDashboard.tsx` (called out in the roadmap slice text) **already have zero `glass-*` and zero `var(--*)` legacy references** — the prose in the roadmap is approximate; the grep evidence is authoritative.

## Recommendation

Three small atomic commits, then verification, then close. Do NOT mix in any S04 work (don't touch `btn-primary`, `text-gradient`, `animate-*`, the `index.css` `.glass*` block itself, or the `:root` legacy palette block — all S04 territory).

1. **T01 — `glass-card` consumers → `Card variant="glass"` or inline equivalent.** 7 sites across 7 files.
2. **T02 — `glass` / `glass-button` chrome on Header & Footer → inline tokenized equivalent.** 7 sites across 2 files.
3. **T03 — `var(--primary-*)` consumers in CookieConsentBanner → semantic tokens.** 3 sites in 1 file.
4. **T04 — close gauntlet** (the 3 S02 grep gates + build + lint + type-check + vitest + Playwright with no `--update-snapshots`).

This sequencing is per-page-style (matches MEM147's Phase-2 plan) but kept atomic: each commit is one logical change set across files, easy to bisect and revert if a single page render goes sideways.

### Why the inline expression instead of always converting to `<Card variant="glass">`

The 6 raw-`<div>` glass-card consumers (Login, Register, ExtensionAuth, NotFound, PrivacyPolicy, TermsOfService) all wrap the panel directly in animated outer chrome (`animate-slideInUp`, `animate-fadeInScale`). Converting to `<Card variant="glass" padding="lg">` works mechanically but introduces a behavior question: `Card` is a `<div>` with no semantic role added — fine — but the `padding="lg"` → `p-8` mapping does NOT cover `p-12` (NotFound) or `p-8 md:p-12` (legal pages) without further `className` overrides that defeat the `padding` prop. Inline keeps the migration mechanical and preserves the exact rendered padding. **Use `Card variant="glass"` only on Home line 385 where the existing call site is already `<Card>`.**

### Two narrow `var(--*)` exceptions to leave in place

- `frontend/src/styles/tokens.css` lines 75 and 84 use `hsl(var(--primary-foreground))` and `hsl(var(--accent-foreground))`. The substring `var(--primary-` matches `var(--primary-foreground)` — **but the success-criteria gate is `var\(--(primary|neutral|accent)-` followed by a shade digit or hyphen**. Quick test: `rg 'var\(--(primary|neutral|accent)-' frontend/src/styles/tokens.css` does match `var(--primary-foreground)`. To keep the gate honest, the canonical M003 close-gauntlet phrasing must be `var\(--(primary|neutral|accent)-(50|100|200|300|400|500|600|700|800|900|950|emerald|amber|rose|purple)\b'` OR the gate must scope the directory to exclude `tokens.css` and `index.css`. **Recommendation for S02 close gauntlet:** scope the gate to consumer dirs only (`frontend/src/pages/`, `frontend/src/components/`, `frontend/src/hooks/`, `frontend/src/contexts/`, `frontend/src/api/`, `frontend/src/lib/`, `frontend/src/utils/`, `frontend/src/__tests__/`) rather than narrowing the regex. Document the chosen form in the gauntlet output so S04 can reuse it.
- `frontend/src/index.css` itself contains every legacy `var(--primary-*)` / `var(--neutral-*)` / `var(--gradient-*)` reference (≈22 hits inside `.glass*`, `.btn-*`, `.card*`, `.input-modern`, `.text-gradient`, etc.). All of this survives until S04. **The S02 gate must scope to consumer files, not `frontend/src/index.css`.**

### Testing landscape — Playwright coverage gap

The 6 existing Playwright specs (admin, build-list, components/kitchen-sink, parts-catalog, price-alerts, price-history) **do not visit any of the S02-touched pages**:

- No spec visits `/`, `/login`, `/register`, `/extension-auth`, `/privacy-policy`, `/terms-of-service`, the 404 catch-all, or any chrome-only render of Header/Footer/CookieConsentBanner.
- The `kitchen-sink` spec exercises `Card` default variant only (line 397, 414 in `_KitchenSink.tsx`) — it does NOT render `Card variant="glass"`.

Implications:
1. **Per-slice Playwright baseline refresh is a no-op for S02.** Running `npx playwright test` after the migration will not surface meaningful diffs on any baseline because no covered baseline depicts a touched page. Don't claim a "baseline refresh" deliverable — claim "manual visual verification" instead.
2. **Visual regression risk for the 9 touched pages is bounded by manual inspection.** The recommended check is: start the dev server (`npm run dev` in `frontend/`, with `backend/` and `docker-compose up -d` running so the home-page stats counts populate), then visit `/`, `/login`, `/register`, `/privacy-policy`, `/terms-of-service`, and 404 at the 3 viewports (`360 / 768 / 1280`) by resizing the Chromium devtools or via Playwright's headed mode. Document a one-line per-page verdict in the slice summary.
3. **No new specs in S02.** Adding spec coverage for these pages is a worthwhile S05/S06 follow-up (or an S06 grep-guard extension), but it's not in scope for S02. Keep the slice tight.

### Visual diffs to expect (and accept)

- Slight chrome shift on Header buttons / Footer social icons / Login/Register/ExtensionAuth/NotFound/PrivacyPolicy/TermsOfService panels: the legacy `.glass*` rules used `background: var(--gradient-glass)` (a 135deg gradient from rgba(255,255,255,0.15) to rgba(255,255,255,0.10)) plus a tinted `box-shadow: 0 8px 32px 0 rgba(31,38,135,0.37)` (purple-blue cast). The semantic equivalent (`bg-white/5 border-white/10 backdrop-blur-xl`) is a flat 5%-white wash with no shadow. The user has already accepted this difference on About / Pricing / Support / ContactUs / Checkout where `<Card variant="glass">` is in production. S02 simply propagates that aesthetic to the holdouts.
- The `glass-button::before` shimmer overlay disappears on Header buttons. No replacement.
- CookieConsentBanner top border + accept-button color: legacy `--primary-500: #3b82f6` and `--primary-600: #2563eb` vs. semantic `--primary` at HSL `217 91% 60%` (≈ #3a8df4) and `bg-primary/90` (~#3a8df4 with 90% alpha over background). At the dark-substrate background the optical difference is ≤2 perceived hue steps — close enough that no user will notice.

## Implementation Notes

### Order of operations within each task

For each consumer file: read the file, apply the mapping table edit, save. After all files in a task are edited, run `rg 'glass-(card|button)?' frontend/src/components/ frontend/src/pages/ frontend/src/contexts/ frontend/src/hooks/ frontend/src/api/ frontend/src/lib/ frontend/src/__tests__/` to confirm zero hits before commit. Same shape for the `var(--*)` gate after T03.

### Pitfalls

- **Don't widen scope.** `btn-primary` (Header line 93, line 188; NotFound line 19) is S04 territory. `text-gradient` (NotFound line 17) is S04. `animate-slideInUp` / `animate-fadeInScale` / `animate-float` / `animate-glow` / `animate-slideInLeft` are all S04. Touching them in S02 makes the slice non-atomic and harder to revert.
- **Don't strip surrounding chrome.** The `<div className="absolute inset-0 overflow-hidden">` decorative bg-blobs above the Login/Register/ExtensionAuth glass panels (lines 160–166 / 73–76 / etc.) use `bg-primary/10` (already semantic) and `bg-purple-500/10` (decorative, S05 polish territory). Leave both alone.
- **Beware `tsconfig.json` `noUnusedLocals` if T01 pulls in `Card` for one site.** Home.tsx already imports `Card` (line 385 references it). Login/Register/ExtensionAuth/NotFound/PrivacyPolicy/TermsOfService do NOT currently import `Card` — and since the recommendation is to keep the `<div>` shape inline rather than convert to `<Card>`, no new imports are needed in those 6 files. T01's diff is therefore confined to `className` strings only.
- **Header line 156's `border border-white/10` already overlaps the legacy `.glass-card` border.** When migrating, drop the duplicate so the new className is `border border-white/10 bg-white/5 backdrop-blur-xl mx-4 mb-4 rounded-xl` — not `border border-white/10 border border-white/10 …`. Mechanical but easy to miss.

### Verification surface (the close-gauntlet for T04)

Run all six commands in sequence; all must return zero hits in consumer dirs:

```

# Bare-glass gate to catch the boundary-map's "Zero `glass-card` / `glass-button` / `glass` references" prose
rg '\bglass\b(?!-)' frontend/src/components/ frontend/src/pages/ frontend/src/contexts/ frontend/src/hooks/ frontend/src/api/ frontend/src/lib/ frontend/src/__tests__/
# Note: the existing `<Card variant="glass">` consumers (About, Pricing, Support, ContactUs, Checkout, the new Home line 385) still match this gate via the literal string `"glass"` inside `variant="glass"`. To exclude those, narrow further: `rg '\bglass\b' --glob '!*.tsx' …` — or accept the matches and confirm by inspection that they're all `variant="glass"`. **Recommended phrasing for the gate: `rg 'className=.*\bglass\b'` which captures only string-literal class consumers, not prop values.**

# var(--*) consumer gate, scoped past tokens.css and index.css
rg 'var\(--(primary|neutral|accent|gradient)-' frontend/src/components/ frontend/src/pages/ frontend/src/contexts/ frontend/src/hooks/ frontend/src/api/ frontend/src/lib/ frontend/src/__tests__/

cd frontend && npm run type-check
cd frontend && npm run lint
cd frontend && npm test -- --run
cd frontend && npm run build
cd frontend && npx playwright test
```

The expected outcome on the Playwright run is "all green, zero baseline drift" because no touched page is screenshotted. If a baseline drifts unexpectedly, that's a real regression — investigate, do NOT auto-rewrite with `--update-snapshots`.
