# T01: Add part_price_alerts model + migration + Pydantic schemas (foundation for S07 price-drop alert loop)

**Add part_price_alerts model + migration + Pydantic schemas (foundation for S07 price-drop alert loop)**

## What Happened

Created the `PartPriceAlert` SQLAlchemy ORM model at `backend/app/api/models/part_price_alert.py` with the schema specified in the task plan: UUID primary key (uuid7 default, indexed), user_id and part_id FKs to users.id and parts.id (both NOT NULL + indexed), threshold_cents int (NOT NULL, CHECK constraint `threshold_cents >= 0` named via op.f for naming-convention compliance), active bool default True, last_fired_at nullable datetime, plus created_at/updated_at lambda-default-UTC timestamps mirroring the PartListing pattern. Added the `UniqueConstraint('user_id', 'part_id', name='uq_part_price_alert_user_part')` to enforce one-alert-per-user-per-part — re-subscribing in T02 will upsert against this constraint. Registered the model in `backend/app/api/models/__init__.py` (alphabetical position between PartListing and PartPriceHistory) and added it to `__all__` so future autogenerate runs see it.

Added Pydantic v2 schemas at `backend/app/api/schemas/part_price_alert.py`: `PartPriceAlertCreate(part_id: UUID, threshold_cents: int = Field(ge=0))`, `PartPriceAlertUpdate(threshold_cents: Optional[int]=None ge=0, active: Optional[bool]=None)`, and `PartPriceAlertRead(...)` carrying every model field with `model_config = ConfigDict(from_attributes=True)` so endpoint code in T02 can serialize ORM rows directly.

Ran `alembic revision --autogenerate -m 'add part_price_alerts'` per CLAUDE.md (NEVER hand-write migrations). The autogenerate pulled in unrelated naming-convention drift (categories_name_key rename plus FK re-namings on parts and build_list_parts) which D-12 / SAFE-09 explicitly says to discard — captured this as MEM086 for future migrations. The committed migration `9aa798d6107e_add_part_price_alerts.py` keeps only the new table + 3 indexes (id, part_id, user_id) and the matching downgrade. Applied with `alembic upgrade head` against the dev Postgres in Docker; alembic current confirms `9aa798d6107e (head)`.

Wrote `backend/tests/models/test_part_price_alert.py` (and a sibling `__init__.py` to make tests/models a package). Ten tests cover: ORM defaults (active=True, last_fired_at=None, timestamps populated); UNIQUE constraint fires IntegrityError on duplicate (user_id, part_id); same user can subscribe to different parts; different users can subscribe to the same part; last_fired_at is writable for cooldown bookkeeping; Pydantic Create rejects negative threshold; Pydantic Create accepts threshold=0; Update is fully partial; Update rejects negative threshold; and Read.model_validate(orm_instance) round-trips correctly via from_attributes=True. The CHECK constraint at the DB layer is intentionally not asserted at the test level because SQLite (the test backend) does not enforce CHECK reliably without explicit pragma — Pydantic ge=0 is the enforced layer at the API boundary, and this is documented in the test file's module docstring.

No runtime observability is in scope for this task (model-only); T03 is where the structured `price_alert_evaluated` and `price_alert_email_sent` logs land.
