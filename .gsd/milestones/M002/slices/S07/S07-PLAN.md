# S07: Price-drop alerts (subscription, threshold, email)

**Goal:** Ship the full price-drop-alert loop: a per-user subscription on a part with a threshold price, an evaluation hook on the price-write path that fires email when the threshold is breached, and frontend surfaces (subscribe button on /parts/:id and a /account/alerts management page) so users can see and remove their own subscriptions.
**Demo:** Subscribe to a part with threshold $X on the part detail page. Trigger an observation below threshold (via test endpoint or manual scrape replay). Email arrives with part details, current price, and unsubscribe link. Visit /account/alerts — subscription listed; click unsubscribe; subscription removed and confirmed by reloading.

## Must-Haves

- Subscribe to a part with threshold $X on the part detail page persists a `part_price_alerts` row scoped to current_user.
- An observation written through `create_or_update_listing_and_price` whose price ≤ threshold synchronously enqueues an email send (mocked at SES boundary in tests; live via existing core/email.py path).
- Email contains: part name, current price, retailer name, link back to the part, and a one-click unsubscribe URL bound to that alert (signed JWT, single-use semantics — alert.active=False after click).
- Visit /account/alerts: lists every active alert for the current user with part name, threshold, created_at, and an unsubscribe button; click → 204 → row disappears on reload.
- Repeat-fire suppression: once an alert has fired (last_fired_at within 24h) it does NOT re-send for subsequent observations under threshold; recovery above threshold resets the cooldown.
- 1 backend pytest file for model+endpoint behavior, 1 backend pytest file for the threshold evaluation service + hook integration, 1 frontend vitest file for the new partPriceAlertsApi client, 1 vitest file for the ViewPart subscribe-button integration, 1 vitest file for the AccountAlerts page, 1 Playwright e2e at /account/alerts subscribe→fire-via-mocked-observation→email-API-call→unsubscribe.

## Verification

- Runtime signals: structured INFO log `price_alert_evaluated: alert_id=<id> part_id=<id> price_cents=N threshold_cents=N verdict=<fired|suppressed_cooldown|skip_above_threshold> elapsed_ms=N` per evaluation; structured INFO log `price_alert_email_sent: alert_id=<id> user_id=<id> success=<bool>`.
- Inspection surfaces: GET /api/part-price-alerts/me returns the current user's alerts with last_fired_at + active flag; the part_price_alerts DB table is the source of truth.
- Failure visibility: send_price_drop_alert_email returns False on SES failure (matches send_verify_email contract); the evaluator logs the False and leaves last_fired_at unchanged so the next observation retries (idempotent retry).
- Redaction constraints: do NOT log user email addresses or unsubscribe tokens; user_id (UUID) is fine.
