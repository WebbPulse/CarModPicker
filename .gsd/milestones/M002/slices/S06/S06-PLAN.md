# S06: Price-history frontend surfaces (sparkline + detail view)

**Goal:** Ship the price-history frontend surfaces — every part-list card with observations renders a sparkline + price-delta line, and the per-part detail view at /parts/:partId shows retailer-by-retailer aggregation (min / max / last / observation count) with a "stale as of <date>" caveat for listings 60+ days old. Zero observations renders no sparkline; a single observation renders a dot. Consumes S05's getBatchPriceHistorySummary (catalog) and getPartPriceHistorySummary (detail) — no new backend code.
**Demo:** Visit /parts in dev — every part card with observations shows a sparkline + delta line. Click a card to drill into the per-part detail view — retailer breakdowns and listing-level history visible, with stale-observation 'as of' caveat where relevant. Inspect a part with zero observations: no sparkline rendered, just current price.

## Must-Haves

- Visit /parts in dev with sample data — every part card with observations shows a sparkline + a "$X → $Y over N days" delta line; parts with zero observations render only the existing best-price cell, no sparkline.
- Click a part card to open /parts/{id} — the existing price-history line chart still renders AND a new "Price by retailer" breakdown block (driven by the new summary endpoint) is visible with min / max / last per retailer; listings whose latest observation is 60+ days old display a "as of <localized date>" caveat.
- Sparkline and PriceDeltaLine render the three observation cardinalities (zero / single / multi) without crashing — covered by vitest + RTL unit tests.
- frontend/e2e/price-history.spec.ts asserts both surfaces with toHaveScreenshot at mobile/tablet/desktop against deterministic mocked API responses; npm run test:e2e exits 0.
- Catalog batch fetch makes ONE POST /parts/price-history request per displayed page (verified by spec) — never one request per card.
- npm run type-check exits 0; npm test passes; no new lint errors introduced (baseline tracked in MEM062).

## Integration Closure

- Upstream surfaces consumed: `frontend/src/api/parts.ts::partsApi.getBatchPriceHistorySummary` (S05 batch endpoint), `frontend/src/api/parts.ts::partsApi.getPartPriceHistorySummary` (S05 single endpoint), `frontend/src/types/Api.ts::PriceHistoryBatchResponse` / `PriceHistorySinglePartResponse` / `RetailerPriceBreakdown`, `frontend/src/components/parts/PartList.tsx` (card + table layouts at lines ~712 and ~876), `frontend/src/pages/builder/ViewPart.tsx` (existing PriceHistoryLineChart integration at line ~638), `frontend/src/components/ui/tabs.tsx` (S08 Tabs primitive used for retailer breakdown switcher).
- New wiring introduced: `usePartPriceSummaries` hook batches the per-page IDs into one POST and memoizes the response map; `PartList.tsx` calls the hook once per displayed page and passes summaries down to each row/card; `ViewPart.tsx` calls `getPartPriceHistorySummary` alongside the existing legacy `getPartPriceHistory` (the legacy call stays — it feeds the existing detail-page line chart) and renders the new retailer-breakdown block.
- What remains before the milestone is truly usable end-to-end: S07 will reuse the new aggregation primitives for alert threshold evaluation; S10 (parts-catalog redesign) will swap the existing PartList rendering onto S08 primitives but the sparkline integration here travels with whatever PartList becomes; S13 milestone-verification runs the live end-to-end flow against a real product.

## Verification

- Runtime signals: existing backend `price_history_aggregation:` INFO log fires on every catalog batch fetch (S05); frontend logs the catalog-page batch request via the existing apiClient interceptor (no new logging needed).
- Inspection surfaces: Browser devtools Network panel shows exactly one POST /parts/price-history per displayed catalog page; React component tree exposes Sparkline + PriceDeltaLine props for inspection; the e2e spec captures the mocked-network log on failure (Playwright trace).
- Failure visibility: when the batch fetch fails, the catalog page falls back to rendering the existing best_price_cents cell unchanged (no broken cards) — surfaced via console.warn from the hook so a future agent can grep logs; the detail view shows "Price history unavailable" inline rather than throwing.
- Redaction constraints: none — price-history responses contain no PII, retailer names, or auth tokens.
